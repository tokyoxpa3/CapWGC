> 日期：2026-10-17
> 編碼機器：RTX 4070 Ti（Ada / 第 8 代 NVENC）/ 驅動 616.92 / RDP session
> 量測機器：RTX 3060 Ti（hostname `tokyo`）/ 驅動 610.88 / console session

## 1. 結論先講

**AV1 在這台機器上端到端跑通了**：Media Foundation 有 `NVIDIA AV1 Encoder MFT`，
自寫的 muxer 現在寫得出 `av01` + `av1C`，檔案用系統 AV1 解碼器解得回來。

| 驗收標準 | 結果 | 數據 |
|---|---|---|
| 有 AV1 硬體編碼器 | **通過** | NVIDIA AV1 Encoder MFT，d3d11-aware |
| 產出的檔案可解 | **通過** | 30 秒 / 949 幀 / 29.938s，decodes OK |
| 對 H.264 的壓縮率 | **高熵 52~59%；UI 63~66%** | 見 §3.4.2（同批錨點，無內插）。舊的 55~63% 混了兩種內容，且 H.264 那一側是壞旋鈕的長弦 |
| 對 HEVC 的壓縮率 | **高熵 91~100%（中位 98%）；UI 反而 101~121%** | 見 §3.4.3（高熵八點，3060 Ti 量完）、§3.4.1（UI 八點）。UI 上 AV1 全面落後 |
| CPU < 1 ms/幀 @720p | **通過** | 0.066 ms/幀（量測已到計時粒度下限） |
| 強制 kill 後檔案仍可播 | **通過** | fMP4 240 幀可解；progressive 回 `0xC00D36C4` |
| `--quality` 改動看得到大小變化 | **通過** | 2.75 → 4.51 → 6.17 MB |

一句話：**AV1 值得當預設，但它在 NVENC 上對 HEVC 沒有優勢，在 UI 內容上還更差**。
高熵內容 AV1 是 HEVC 的 91~100%（中位 98%，也就是省 0~9%）；UI 內容反過來，
AV1 是 101~121%（中位約 107%）。比規格書講的 20~30% 小一個量級，方向還相反。
真正的落差在 AV1 對 H.264，而 HEVC 對 H.264 就已經拿走大部分好處：
**H.264→HEVC 這一步賺到的最多，HEVC→AV1 在高熵只再多 0~9%，在 UI 上是負的**。

> **2026-10-17 第二輪修訂**：AV1 對 H.264 的比值重測了。這張卡的 H.264 quality 旋鈕
> 既不單調也不連續（同批幀下 QP 16 → QP 15 跳 7.39 dB，q80 → q85 多花 20% 位元
> 卻掉 0.18 dB），所以「掃一條曲線再內插」的結果全部作廢，改成同批匹配 PSNR 直接
> 量比值。UI 是 **63~66%**、高熵是 **52~59%** —— UI 沒有 55% 那麼好，而且比值
> 隨畫質上升而變動，不是一個常數。詳見 §3.4.2。

## 2. 實作了什麼

### 2.1 AV1 在容器層是完全不同的東西

| | H.264 / HEVC | AV1 |
|---|---|---|
| access unit 結構 | Annex-B 起始碼 + NAL | 一串 OBU，每個自帶 `obu_size`（leb128） |
| 參數集 | VPS/SPS/PPS | 單一個 sequence header OBU |
| 寫進 mdat 前 | Annex-B → AVCC（換成 4-byte 長度前綴） | **原樣**，一個 byte 都不改 |
| sample entry | `avc1`+`avcC` / `hvc1`+`hvcC` | `av01` + `av1C` |
| 關鍵幀判定 | NAL type 5 / 16~21 | frame header 的 `frame_type == KEY_FRAME` |

結果是 AV1 的 muxer 路徑**比 HEVC 短**：不用拆 NAL、不用重寫長度前綴、不用從
in-band 參數集組 config record。`WriteSample()` 裡 AV1 分支只做三件事 ——
找 sequence header 組 `av1C`、判關鍵幀、把整個 AU 原樣塞進 mdat。

### 2.2 av1C 的欄位要真的去解 sequence header

`av1C` 需要 profile / level_idx / tier / high_bitdepth / mono / 色度取樣這幾個值，
全部藏在 sequence header OBU 的位元流裡。實作是一個 bit reader 走完
`sequence_header_obu()` 直到 `color_config()`。

實測這台機器產出的值（1296×740，720p 級）：

```
av1C = 81 09 0c 00   configOBUs = 0a 0c 00 00 00 4a a6 87 dc 7c 00 21 98 04
       │  │  │  └ reserved + initial_presentation_delay_present = 0
       │  │  └── tier=0(Main) highbd=0 12bit=0 mono=0 subX=1 subY=1 csp=0
       │  └───── seq_profile=0(Main) seq_level_idx=9(4.1)
       └──────── marker=1 version=1
```

level 4.1 / Main tier / 8-bit 4:2:0，對 720p60 是合理的值 —— 這行「合理」本身就是
驗證，因為錯位的解析會給出 level 18 + high tier 這種不存在的組合（見 §4.1）。

### 2.3 碼控：AV1 的 QP 上界是 63，不是 51

`CODECAPI_AVEncVideoMinQP/MaxQP` 在 AV1 MFT 上回報的合法區間是 **1..63**
（H.264/HEVC 是 0..51）。沿用 51 會把整個低碼率區間截掉 —— 檔案偏大，但畫面對
錄屏來說「看起來沒問題」，是最不容易被發現的那種錯。

quality → QP 的映射目前是：

```
H.264  qp = 51 - 0.50·q
HEVC   qp = 51 - 0.44·q
AV1    qp = 63 - 0.62·q      (q≥99 一律 QP 1)
```

斜率 0.62 原本是照「q60 對齊 HEVC」挑的，但當時手上的 HEVC 47.60 dB 是別台量出來的
數字。同一批幀重新量之後（見 §3.4），實際偏差是 **q40 +0.94 dB、q60 -0.83 dB、
q75 -2.22 dB** —— 三個點都不齊，而且 q75 差了 2.2 dB，比原本估計的 1.1 dB 嚴重。

反推「要對齊 HEVC 畫質」所需的斜率：q40 要 0.57、q60 要 0.645、q75 要 0.675。
斜率一路往上，正是「AV1 的 rate-QP 曲線比 HEVC 平」的意思 —— 一條直線對不齊
三段，要分段或查表（見 §5.2）。

## 3. 實測數據

### 3.1 測試條件

- 720p 級（RDP 桌面只有 1280×720，1080p 這台測不了）
- 每組 6 秒、約 185 幀、RDP 下擷取 31 fps
- **同一批幀同時餵給兩個編碼器**（`--ab`），外加一份 q100 H.264 當近無損參考
- PSNR 是 luma、逐幀平均，對參考檔比對

### 3.2 高熵內容（`anim_window --hard`，1296×740）

| quality | AV1 | AV1 PSNR | HEVC | HEVC PSNR | H.264 | H.264 PSNR |
|---|---|---|---|---|---|---|
| 40 | 2.75 MB | 41.80 dB | 2.71 MB | 40.86 dB | 3.52 MB | 39.49 dB |
| 60 | 4.51 MB | 47.75 dB | 4.81 MB | 48.58 dB | 7.34 MB | 46.52 dB |
| 75 | 6.17 MB | 52.80 dB | 7.56 MB | 55.02 dB | 11.45 MB | 57.12 dB |

HEVC 那欄的 PSNR 是 2026-10-17 在 3060 Ti 那台補量的（這台沒有 HEVC 解碼器），
檔案與參考檔同批、時間軸對齊 `index + 0`，可以直接比。

換算成「同等 PSNR 下的檔案大小比」：

| 目標 PSNR | AV1 | H.264 | AV1 / H.264 |
|---|---|---|---|
| 41.8 dB | 2.75 MB | 4.78 MB | **57.6%** |
| 47.8 dB | 4.51 MB | 7.82 MB | **57.7%** |
| 52.8 dB | 6.17 MB | 9.78 MB | **63.1%** |

**AV1 是同畫質下 H.264 的 58~63%**，而且 q40/q60 兩列是「兩個軸都贏」
（更小、還更高 PSNR）。這比 HEVC 對 H.264 的 63~75% 再好一截。

### 3.3 真實 UI 內容（Chrome 視窗，1296×696，文字為主）

| quality | AV1 | AV1 PSNR | HEVC | HEVC PSNR | H.264 | H.264 PSNR |
|---|---|---|---|---|---|---|
| 60 | 0.104 MB | 48.13 dB | 0.123 MB | 50.59 dB | 0.183 MB | 48.67 dB |
| 75 | 0.158 MB | 51.67 dB | 0.299 MB | 54.47 dB | 0.436 MB | 55.95 dB |

同畫質下 AV1 ≈ H.264 的 **55~64%**。

> **這一段的 55% 已經作廢（2026-10-17 第二輪）**。它靠 H.264 的 q60/q75 兩點拉直線，
> 跨了 7.3 dB。補點之後發現 H.264 的旋鈕本身不單調，長弦算出來的 55% 是錯的；
> 改用同批匹配 PSNR 直接量，UI 是 **63~66%**（見 §3.4.2）。下表保留是為了
> 對照「舊數字怎麼來的」。

**HEVC 在這組的 PSNR 比 AV1 高 2.5~2.8 dB。** 所以 q75 時「AV1 只有 HEVC 的 53%」
這個數字，是在 HEVC 畫質明顯更好的前提下比出來的。這兩個點只夠做粗略換算 ——
補成八個點之後的真實答案是 AV1 **反而大 1~21%**，見 §3.4.1。原本「UI 內容才是
AV1 的主場、可省 20~45%」的說法不成立。

### 3.4 AV1 對 HEVC 的同畫質比較（重點，2026-10-17 補齊）

> 量測在 **3060 Ti 那台**（hostname `tokyo`，有 HEVC 解碼器）：
> `mp4_check R40a.mp4 H40.mp4`、`R60a/H60`、`R75a/H75`、
> `UR60a/UH60`、`UR75a/UH75`。檔案與參考檔同批 `--ab` 產出，時間軸對齊
> `index + 0`，幀數與參考檔一致，五個測試檔全部解得開。

**高熵（`--hard`，183~184 幀）**

| 目標 PSNR | AV1 | HEVC | AV1 / HEVC | H.264 | AV1 / H.264 |
|---|---|---|---|---|---|
| 41.80 dB | 2.75 MB | 2.96 MB | **92.7%** | 4.78 MB | 57.5% |
| 47.75 dB | 4.51 MB | 4.58 MB | **98.4%** | 7.82 MB | 57.7% |
| 52.80 dB | 6.17 MB | 6.61 MB | **93.3%** | 9.78 MB | 63.1% |

> **這張表只有三個點，已被八點版取代。** 定稿數字看 §3.4.3：**91~100%，中位 98%**。
> 本表保留是為了對照 —— 長弦在低碼率那端把 HEVC 算便宜了 2 個百分點（92.7% → 90.6%）。

**UI 內容**：原本只有 q60/q75 兩個點，算出 51.67 dB 時 AV1 是 91.7%。這個數字
後來被證明是兩點內插的假象 —— 補成八個點之後是 104%，**AV1 反而落後**。
見 §3.4.1，那節才是 UI 的定稿。

換算方法與 §3.2 對 H.264 用的完全相同（PSNR 軸上對檔案大小分段線性插值）。
拿它重算 AV1/H.264 得到 57.5 / 57.7 / 63.1%，與 §3.2 已公布的 57.6 / 57.7 / 63.1%
一致，所以方法本身沒有偏。改用對數內插（rate-distortion 更常用的做法）則得到
94.6 / 99.8 / 95.4% —— **兩種插值法都指向「沒有顯著優勢」**。

**高熵結論（三點版）：AV1 對 HEVC 幾乎打平，2~8%。**
八點量完之後修正成 **91~100%、中位 98%**，而且不是常數（低碼率端省 9%，46 dB 附近歸零）。
詳見 §3.4.3。

本節改版前寫的「高熵 82~101%、UI 53~83%」是**同一個 quality 旋鈕**下的大小比。
那個比法在 q75 特別吃虧：AV1 52.80 dB 對 HEVC 55.02 dB，AV1 少了 2.2 dB 畫質，
檔案當然小。同畫質校正之後，82% 變成 93%。

**真正的落差在 AV1 對 H.264（55~63%）**，而 HEVC 對 H.264 已經有 59~71%
（用同樣方法重算：63.5 / 59.1 / 71.1%）。也就是說 H.264→HEVC 拿到了大部分好處，
HEVC→AV1 在高熵內容上只再多 0~9%（八點版，中位 2%）。

**可信度**：高熵那組三個目標 PSNR 都落在相鄰的實測區間內，可信 —— 但它也只有三個
點（q40/q60/q75）。UI 組的經驗（§3.4.1）證明 15 個 quality 的間隔可以藏住 18% 的
曲率，所以高熵那組後來也做了 dense sweep（q40~q75 八點，見 §3.4.3）。
結果：**三點沒有算錯方向，但低碼率那端被長弦壓了 2 個百分點**，而且比值不是常數。

UI 那組原本只有兩個點、PSNR 區間幾乎不重疊（AV1 的 48.13 dB 比 HEVC 最低的
50.59 dB 還低，外插給出 878% 這種垃圾值）。已補成八個點，見 §3.4.1 —— 結論是
**AV1 反而落後**，不是打平。

**不要把 82% / 53% 這兩個數字對外講。** 目前站得住的說法：高熵內容 AV1 是 HEVC 的
91~100%（省 0~9%，中位 2%）；UI 內容 AV1 比 HEVC 多花 1~21%；對 H.264 省 34~48%。

### 3.4.1 UI 曲線補點（2026-10-17 量完，結論翻轉）

補了 q65/q70/q80，另外多補 q85/q90/q95 —— 因為 HEVC q75 的 54.5 dB 已經超過
AV1 q80 的 52.68 dB，只補到 q80 的話上面那端還是得外插。

檔案在 `out/ui_sweep/`（每個 quality 一份 AV1 + 一份 HEVC + 一份 q100 參考），
`compute.py` 會自己呼叫 `mp4_check` 量完 24 個檔並印出三張表，**超出範圍標 `OUT`
而不外插**。

**先驗證內容沒漂移**，否則新舊點不能併成一條曲線：

| quality | 新 AV1 | 舊 AV1 | 新 HEVC | 舊 HEVC | 新 AV1 PSNR | 舊 AV1 PSNR |
|---|---|---|---|---|---|---|
| 60 | 106 688 B | 109 103 B | 127 636 B | 129 445 B | 48.11 dB | 48.13 dB |
| 75 | 166 024 B | 165 790 B | 318 732 B | 314 009 B | 51.66 dB | 51.67 dB |

差 2% 內、PSNR 差 0.02 dB —— 同一個頁面、同一組設定，可以直接併。

**實測（3060 Ti，188 幀上下，時間軸全部 `index + 0`）**

| quality | AV1 bytes | AV1 PSNR | HEVC bytes | HEVC PSNR | 同旋鈕比（僅對照） |
|---|---|---|---|---|---|
| 60 | 106 688 | 48.11 dB | 127 636 | 50.60 dB | 83.6% |
| 65 | 123 471 | 49.51 dB | 181 357 | 52.38 dB | 68.1% |
| 70 | 135 529 | 50.37 dB | 223 595 | 53.43 dB | 60.6% |
| 75 | 166 024 | 51.66 dB | 318 732 | 54.54 dB | 52.1% |
| 80 | 210 141 | 52.68 dB | 419 667 | 55.36 dB | 50.1% |
| 85 | 287 312 | 53.98 dB | 503 665 | 55.76 dB | 57.0% |
| 90 | 409 562 | 55.25 dB | 699 407 | 56.45 dB | 58.6% |
| 95 | 702 707 | 56.03 dB | 737 966 | 56.49 dB | 95.2% |

AV1 的 PSNR 在 4070 Ti 上量過一次，這次在 3060 Ti 用另一個解碼器重跑，八個值一字
不差 —— 跨機器、跨解碼器都對得上，這組數字可以信。

**同畫質比（在 HEVC 的每個 PSNR 上內插 AV1 的大小）**

| HEVC 點 | PSNR | HEVC bytes | AV1 @同PSNR | AV1 / HEVC |
|---|---|---|---|---|
| q60 | 50.60 dB | 127 636 | 140 966 | **110.4%** |
| q65 | 52.38 dB | 181 357 | 197 165 | **108.7%** |
| q70 | 53.43 dB | 223 595 | 254 663 | **113.9%** |
| q75 | 54.54 dB | 318 732 | 341 218 | **107.1%** |
| q80 | 55.36 dB | 419 667 | 450 903 | **107.4%** |
| q85 | 55.76 dB | 503 665 | 601 234 | **119.4%** |
| q90 / q95 | 56.45 / 56.49 dB | — | OUT（超出 AV1 上限 56.03 dB） | — |

反過來在 AV1 的五個點上取樣 HEVC，得到 104.0 / 108.6 / 106.1 / 100.8 / 121.1%
（q75~q95），兩個方向一致。改用對數內插只差 1~3 個百分點。

**結論：UI 內容上 AV1 全面落後，多花 1~21%，中位約 7%。沒有交叉點。**

「兩條曲線會交叉、51.7 dB 時 AV1 只要 92%」是**舊的兩點內插造成的假象**。真實的
HEVC 曲線在 q60→q75 之間是凹的：

| 在 52.38 dB 的 HEVC 大小 | bytes |
|---|---|
| 舊算法（q60 與 q75 拉一條直線） | 213 975 |
| 實測 q65 | **181 357** |

直線高估了 18%。因為 HEVC 在 q60→q65 這一段特別划算（+42% 位元換 +1.78 dB），
到 q70→q75 才變貴（+43% 換 +1.11 dB）。兩點連線把中段全部算貴，於是「AV1 要多少
位元才追得上」被高估 —— 91.7% 就是這樣來的，補點之後同一個 PSNR 變成 104%。

**機制**：同一個旋鈕下 HEVC 的 PSNR 高 2.5~2.8 dB，等於 AV1 的曲線整體右移。
AV1 在低 PSNR 端的斜率其實比較陡（每 10% 位元 +0.89 dB，HEVC 只有 +0.42），所以
一路追到 55.2 dB 時幾乎追平（100.8%）；再往上 AV1 先飽和（+72% 位元只換 +0.78 dB），
又被拉開到 121%。規格上 AV1 的 palette / intra block copy 應該在這種「大面積同色 +
重複文字」的內容上發威，但 NVENC 的即時編碼器顯然沒把它換成實際碼率。

**q90/q95 不要用**：HEVC q90→q95 只大 5.5%（699 407 → 737 966）卻只多 0.04 dB，
已經飽和；AV1 那一段大 71%。兩邊的飽和點不同，這段比值沒有意義。q85 的 119.4%
也是 AV1 自己在飽和，不是 HEVC 的問題。**能用的區間是 q60~q80（50.6~55.4 dB），
AV1 是 HEVC 的 104~114%。**

### 3.4.2 UI 的 H.264：補點補出來了，但旋鈕本身是壞的（2026-10-17 第二輪）

上一輪的待辦是「UI 的 H.264 只有 q60/q75，所以『AV1 ≈ H.264 的 55%』裡只有
48 dB 那個點直接可比」。補 q65/q70/q80 的過程中撞到一個更根本的問題：
**這張卡的 H.264 quality 旋鈕不是單調的，也不是連續的。**

#### 先確認不是量測錯

三種下法都試過（原生 Quality、Quality + 釘死 QP、UnconstrainedVBR + 釘死 QP），
前兩種在重疊處互相吻合：

| 下法 | 設定 | 51.2 dB 時的檔案 |
|---|---|---|
| 原生 Quality | 只給 `CODECAPI_AVEncCommonQuality` | q95 → 281 761 B |
| Quality + 釘死 QP | 再加 `MinQP=MaxQP=18` | 282 326 B |

差 0.3%，PSNR 都是 51.19/51.20 dB —— 兩條路徑落在同一條 rate-PSNR 前緣上。
所以量測、對齊（全部 `index + 0`）、參考檔都沒有問題。壞的是旋鈕。
第三種（`--qp`，UnconstrainedVBR + `MinQP=MaxQP`，位元率上限拉到不觸發）也一樣
不單調，所以不是「我們釘 QP 的方式」造成的。

#### 非單調點：同一批幀、同一個參考檔

UI 內容（Chrome 1296×696），每一列都是同一次錄製的兩個編碼器：

| 對照 | A | B | 結果 |
|---|---|---|---|
| 原生 Quality q80 vs q85 | 180 128 B / 49.05 dB | 216 953 B / 48.87 dB | 多花 20% 位元，**掉 0.18 dB** |
| 原生 Quality q95 vs q96 | 281 761 B / 51.20 dB | 294 874 B / 54.04 dB | 多花 4.7% 位元，**+2.84 dB** |
| 釘死 QP 17 vs 16 | 298 036 B / 54.03 dB | 325 851 B / 50.19 dB | 多花 9.3% 位元，**掉 3.84 dB** |

`+2.84 dB` 只多 4.7% 位元、`-3.84 dB` 多花 9.3% 位元，兩個方向都超出任何正常的
rate-distortion 關係。高熵內容同樣有：QP 16 → 47.32 dB / 11.48 MB，
QP 15 → 54.71 dB / 12.08 MB，**一個 QP 步長跳 7.39 dB**（同批、同參考檔）。

確認用的不是軟體編碼器：`[mft] H.264 [NVIDIA H.264 Encoder MFT]`，
`MFT_ENUM_FLAG_HARDWARE` 只列硬體 MFT，所以就是 NVENC。

**機制沒有定論。** 最可能是 MFT 在 Quality 模式底下會自己挑內部 preset（lookahead /
multi-pass 的開關），preset 一換，同一個 QP 就換到另一條曲線上；也可能是低 QP 端
有 in-loop 濾波器或 transform 的門檻。三種下法都受影響，所以不是我們釘 QP 造成的。
要繼續查得有 NVENC SDK 層的 log，不在這台的範圍內。

#### 因為旋鈕壞了，改用「同批錨點」量比值

既然不能靠掃一條曲線再內插，就讓兩個編碼器**吃同一批幀、落在同一個 PSNR**，
比值直接是檔案大小比，一次內插都不用。

指令長這樣（`--no-pin-qp` 兩邊都給，重點是同一批）：

```bat
CapCli.exe --hwnd <hwnd> --codec av1 --quality 60 --ab h264 --q2 77 ^
           --ref ref.mp4 --out av1.mp4 --out2 h264.mp4 --seconds 6 --no-pin-qp
```

補點後同一個 PSNR 是 90.6% —— 長弦把 HEVC 算便宜了（3.11 MB 對實際的 3.35 MB），
比值就被抬高 2 個百分點。方向跟 UI 組（§3.4.1）相反：那次長弦讓 AV1 看起來**太差**，
這次讓 AV1 看起來**太好**，但原因一樣 —— 弦切在凹曲線上。

**跨批不可比**：這批的絕對大小比原本 q40/q60/q75 那批大 5~13%（AV1 q40 3.03 MB 對
2.88 MB），PSNR 卻只差 0.3 dB 以內。內容是重錄的，所以**跨批只能比比值，不能比絕對
大小**。

## 4. 兩個 bug（症狀都不指向自己）

### 4.1 sequence header 的 bit 錯位

`decoder_model_info_present_flag` **只在 `timing_info_present_flag == 1` 時才存在**。
無條件讀它會讓後面每一個欄位偏一個 bit。

症狀：`av1C` 解出 `seq_level_idx=18` + `high tier` —— 對 720p 來說是不存在的組合。
更糟的是**檔案照樣能播**，因為解碼器讀的是 sequence header 本身，不是 av1C 這幾個
提示欄位。所以這個 bug 不會自己浮出來，只會在嚴格解析器或跨工具時咬人。

修法：把 `decoder_model_info_present_flag` 移進 `timing_info_present_flag` 的分支裡。
另外加了一道保險 —— 解析完拿 `max_frame_width/height` 跟實際設定的解析度對一次，
不一致就印警告。這是唯一能免費抓到「bit 讀錯位」的方法。

### 4.2 AV1 解碼器的輸出是 DXGI surface，`GetCurrentLength()` 回 0

`mp4_check` 原本用 `IMFMediaBuffer::GetCurrentLength()` 當緩衝區上界，做
「這一幀的尺寸合理嗎」的檢查。AV1 解碼器給的是 DXGI surface 形式的緩衝，
長度由 surface 決定，`GetCurrentLength()` 回 **0**，於是每一幀都被判成壞帧：

```
[dec] implausible frame: 1280x720 pitch=1280 len=0
```

修法：`GetCurrentLength()` 回 0 時改用 `GetMaxLength()`。這是探測工具的問題，
不是 muxer 的問題 —— 但它的錯誤訊息長得跟「容器壞了」一模一樣。

## 5. 限制與還沒做的

### 5.1 HEVC 的 PSNR 要在另一台量（已於 2026-10-17 補齊）

這台機器**沒有 HEVC 解碼器**：`probe_encoders.exe` 的 decoder 段只有
`Microsoft H264 Video Decoder MFT`。Windows 的 HEVC 解碼是商店擴展
（HEVC Video Extensions，付費），`winget` 安裝回 `0x803f8001`。
AV1 解碼這邊沒問題（AV1 Video Extension 免費，已安裝）。

補法是**編碼在這台、量測在 3060 Ti 那台**：把 `out/R*.mp4`、`out/H*.mp4`、
`out/UR*.mp4`、`out/UH*.mp4` 一起帶過去跑 `mp4_check`。已補完，結果在 §3.4 ——
五個測試檔（H40/H60/H75、UH60/UH75）全部解得開，時間軸對齊 `index + 0`，
沒有容器問題。

換算腳本留在 `out/iso_psnr.py`，改裡面的數字就能重跑（含內插／外插標記）。

順帶一提：`docs/05-m2-status.md` 的 HEVC 數字本來就是在 3060 Ti 那台量的。

### 5.2 其他

- ~~**UI 內容的 RD 曲線只有兩個點**~~ **已補齊（2026-10-17）**：4070 Ti 補產
  q65/q70/q80（另加 q85/q90/q95）放在 `out/ui_sweep/`，3060 Ti 跑 `compute.py`

  **52~59%**。舊的「55%」是高熵組的數字被套到 UI 上，作廢。
- **H.264 旋鈕的根因還沒找到**：三種下法（原生 Quality / Quality+釘死 QP /
  UnconstrainedVBR+釘死 QP）都重現同一個不連續，所以不是我們的設定造成的。
  要往下查得有 NVENC SDK 層的 log 或另一張卡的對照。在搞清楚之前，
  **H.264 只能當「取樣點」用，不能當連續軸。**
- **B 幀**：AV1 MFT 的 `BPictureCount` 也回 `E_NOTIMPL`（跟 HEVC 一樣），
  所以 AV1 目前也沒有 B 幀。這是 MF 包裝層的限制，不是 AV1 的限制。
- **10-bit / 4:4:4**：目前只走 8-bit 4:2:0（NV12 輸入）。
- **1080p / 4K 沒測**：這台的桌面只有 1280×720（RDP），解析度上不去。
  NVENC 的 AV1 官方標稱 8K60，實際要等有 1080p 以上桌面的機器。
- **`--codec auto` 現在會選 AV1**：這是原本就寫好的優先序（AV1 > HEVC > H.264），
  在這台第一次真的生效。相容性考量（舊播放器、Windows 內建播放器）要不要把
  HEVC 擺前面，是產品決策，不是技術限制。

## 7. 環境踩坑（這台專屬）

| 坑 | 症狀 | 解法 |
|---|---|---|
| 這台沒有 C++ 工具鏈 | `build.bat` 回「no MSVC toolset found」，但 `out\` 裡有舊 exe（從別台帶來的） | 裝 VS BuildTools 2022 + VCTools 工作負載（含 SDK 10.0.26100） |
| `anim_window` 用了 `WS_EX_TOOLWINDOW` | `CreateForWindow` 回 `0x80070057`（E_INVALIDARG），看起來像 hwnd 給錯 | 拿掉 `WS_EX_TOOLWINDOW`。Windows 11 24H2 的 WGC 不接受 tool window |
| 沒有 HEVC 解碼器 | `mp4_check` 對 HEVC 檔回 `SetCurrentMediaType(NV12) 0xC00D5212` | 商店的 HEVC 擴展要付費；AV1 擴展免費，已裝。改到 3060 Ti 量，見 §5.1 |
| 想「在 3060 Ti 上重錄 HEVC 來量」 | 動畫相位不同，PSNR 只有 21 dB | 不能重錄。要量的是 4070 Ti 產出的**那幾個檔案**，把 mp4 連同參考檔一起帶過去 |
| 用兩個 quality 點內插算「同畫質比」 | UI 組算出 91.7%，補到八個點後變成 104%，差 12 個百分點；高熵組三點算出 92.7%，補到八點是 90.6% | rate-PSNR 曲線是凹的，長弦會把中段算貴（或算便宜）。同畫質比至少要 5~6 個點、相鄰間隔 ≤5 個 quality，超出範圍寧可標 OUT 也不外插 |
| 以為 quality 是連續旋鈕 | NVIDIA H.264 MFT 同批幀下 QP 16→15 跳 7.39 dB、q80→q85 多花 20% 位元卻掉 0.18 dB | 旋鈕分段（內部 preset 會切換）。H.264 只能取樣點、不能掃曲線；要比比值就用同批匹配 PSNR，見 §3.4.2 |
| 參考檔跟著 `--no-pin-qp` 一起鬆掉 | 參考檔只剩 325 KB（釘死 QP1 是 1 126 KB），同一批 q65 量到 47.57 dB 而非 51.19 dB | 尺本身有損就量不到真值。`q >= 99` 一律釘死 QP 1，不受 `--no-pin-qp` 影響 |
| 跨批次併曲線 | 高熵組兩次錄製的參考檔 19.7 MB vs 21.7 MB（差 10%），PSNR 只剩 17 dB | 動畫相位每次不同。跨批次只能比「統計上等價」，要算比值就得同批 |
